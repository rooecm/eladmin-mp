# Spring Boot 3 前后端分离项目：基础认证与权限管理实现方案

> **文档用途：** 交由 AI Agent 在现有项目中实施。\
> **方案目标：**
> 在保证安全性和可维护性的前提下，优先采用简单、易理解的实现，不提前建设复杂的认证框架。\
> **技术基线：** JDK 17、Spring Boot 3.x、Spring Security
> 6.x、Redis。具体依赖版本应由项目当前 Spring Boot BOM
> 管理，不要手工混用不兼容版本。

------------------------------------------------------------------------

## 1. 目标与范围

### 1.1 第一阶段必须实现

- 用户名、密码登录。
- 使用 BCrypt 校验密码，不保存明文密码。
- 登录成功后生成高强度随机、不透明 Token。
- 将 Token 对应的登录状态存入 Redis，并设置过期时间。
- 前端携带 Token 访问受保护 API。
- 每次请求验证 Token 是否仍然有效。
- 当前用户信息查询。
- 当前 Token 登出；登出后该 Token 立即失效（对之后发起的新请求生效）。
- RBAC 权限校验。
- URL 级别访问控制及方法级 `@PreAuthorize` 权限控制。
- 统一处理未认证（401）和无权限（403）响应。
- 浏览器、App、小程序可以复用同一套后端认证与授权能力。

### 1.2 第一阶段明确不实现

以下功能不在本阶段范围内，不要为了"预留扩展"而提前实现：

- 多端登录策略引擎。
- 同端顶号、跨端顶号。
- 管理员踢人、全端下线。
- 设备会话注册表和复杂会话索引。
- OAuth2 授权服务器、SSO、第三方登录。
- JWT 黑名单或 JWT + Redis 双重校验。
- 复杂的策略 DSL、脚本执行或规则引擎。

后续需要多端会话管理时，再在现有 Token 服务之上扩展会话管理能力。

## 2. 实现原则

1. **优先使用 Spring Security 原生机制。** 使用
   `AuthenticationManager`、`UserDetailsService`、`PasswordEncoder`、`SecurityFilterChain`
   和 `SecurityContext`，不要重新实现一套认证框架。
2. **认证与授权分离。**
   过滤器负责建立当前请求的认证身份；接口权限由请求授权规则和
   `@PreAuthorize` 处理。
3. **Token 采用随机不透明 Token。** Token
   不携带可被客户端直接解析信任的用户权限信息，服务端通过 Redis
   判断登录状态。
4. **保持实现简单。**
   不要为每个类再增加接口、工厂、策略或管理器。只有现有项目的架构约束、真实替换需求或测试需求明确要求时才增加抽象。
5. **复用现有用户和 RBAC 模型。** 不要重复创建一套用户、角色、权限表。
6. **适配现有项目。**
   实现前先检查项目目录、模块边界、统一响应对象、错误码、数据库访问方式、Redis
   封装和现有权限模型；不要擅自重构无关模块。
7. **安全默认拒绝。** 除明确放行的登录等接口外，其余 API
   默认需要认证；业务权限必须在后端验证。

## 3. 推荐结构

以下是逻辑职责示例，不要求必须建立同名 Maven
模块。应优先遵循现有项目的分层和命名约定。

``` text

├── TokenAuthenticationFilter.java
├── LoginUser.java
├── UserDetailsServiceImpl.java
├── AuthenticationEntryPointImpl.java
└── AccessDeniedHandlerImpl.java

auth/
├── AuthController.java
├── AuthService.java
└── TokenService.java
```

如果项目已经有对应类或公共组件，应复用现有实现，避免重复。

  ----------------------------------- ----------------------------------------------------------------------------------

## 4. 认证方案

### 4.1 登录流程

1. 客户端提交用户名和密码。
2. `AuthService` 调用 `AuthenticationManager.authenticate(...)`。
3. Spring Security 通过 `UserDetailsServiceImpl` 加载用户和权限，并使用
   `PasswordEncoder` 校验密码。
4. 认证失败时返回统一的认证失败响应；不要泄露用户名是否存在、密码是否正确等过多细节。
5. 认证成功后，生成密码学安全随机 Token。
6. 在 Redis 保存 Token 对应的用户标识及必要的会话信息，并设置 TTL。
7. 返回 Token 和必要的用户信息、权限信息。

示例认证调用：

``` java
Authentication authentication =
        authenticationManager.authenticate(
                new UsernamePasswordAuthenticationToken(
                        username, password
                )
        );
```

登录成功后从 `authentication` 中取得认证主体。不要在 Controller
中自行查询密码并手工比较。

### 4.2 Token 设计

- 使用 `SecureRandom` 等密码学安全随机数生成器生成高熵 Token。
- Token
  使用不透明随机字符串，不包含用户密码、角色、权限或其他敏感信息。
- 建议对 Token 做 SHA-256 摘要后再作为 Redis Key，避免原始凭证出现在
  Redis 键名中。
- 原始 Token 只在登录成功响应中返回给客户端；不要写入日志。
- Redis Key 示例：`auth:token:{tokenDigest}`。
- Redis Value 只保存必要信息，例如用户
  ID、签发时间、过期时间或会话标识。不要保存密码。
- 为 Redis Key 设置 TTL。TTL 应与系统配置的 Token 有效期一致。
- Token 的生成、摘要、保存、验证和撤销统一由 `TokenService` 管理。

不要将 Token 直接当作用户 ID 使用，也不要仅凭客户端传入的用户 ID
判断身份。

### 4.3 请求认证流程

1. 客户端在请求头中发送 `Authorization: Bearer <token>`。
2. `TokenAuthenticationFilter` 读取 Bearer Token。
3. 如果没有 Token，则不建立认证上下文，交由 Spring Security
   的授权规则决定是否允许匿名访问。
4. 如果 Token 存在，调用 `TokenService` 检查其 Redis 状态。
5. Token 不存在、已过期或已撤销时，不得建立已认证身份。对于受保护
   API，最终返回统一 401。
6. Token 有效时，加载当前用户及当前权限，构建 `Authentication` 并设置到
   `SecurityContextHolder`。
7. 后续由 Spring Security 执行 URL 规则和方法级权限检查。

过滤器不要实现业务权限判断，也不要吞掉异常后继续把请求当作已认证用户处理。每个请求结束时，应遵循
Spring Security
的上下文清理机制；不要自行将用户身份保存到跨请求的线程状态。

### 4.4 Token 登出

- `POST /api/auth/logout` 需要认证。
- 从当前请求上下文取得本次使用的 Token，撤销对应 Redis Key。
- 返回统一成功响应。
- 登出后，该 Token 的后续新请求必须认证失败。
- 不要仅在客户端删除 Token 而不撤销服务端状态。

## 5. Spring Security 配置要求

使用 `SecurityFilterChain` Bean 配置，不要使用已废弃的
`WebSecurityConfigurerAdapter`。

基本要求：

- 使用 `SessionCreationPolicy.STATELESS`，因为本方案使用 Bearer Token
  和 Redis 状态，不依赖 Servlet HttpSession 保存登录状态。
- 仅对明确的公开 API 使用
  `permitAll()`，例如登录、必要的验证码或健康检查接口。
- 其他请求默认要求认证。
- 配置 `AuthenticationEntryPointImpl` 和 `AccessDeniedHandlerImpl`。
- 配置 `PasswordEncoder`，推荐 `BCryptPasswordEncoder`。
- 启用方法级权限：`@EnableMethodSecurity`。
- 按正确顺序将 Token 过滤器加入 Spring Security 过滤链，通常位于
  `UsernamePasswordAuthenticationFilter` 之前。
- 不要重复注册同一个过滤器为 Servlet Filter 和 Security
  Filter，避免执行两次。
- 不要在过滤器中自行编写 401/403 的多套 JSON
  格式，统一交给异常处理组件。

### CSRF 注意事项

不能因为项目是前后端分离就无条件禁用 CSRF。

- 如果 API 只使用显式添加的 Bearer
  Token，且认证凭证不会由浏览器自动附带，可以根据实际部署方式评估禁用
  CSRF。
- 如果浏览器使用 Cookie 自动携带认证凭证，必须评估并实施 CSRF 防护。
- Cookie 方案应正确配置 `HttpOnly`、`Secure`、`SameSite`、跨站策略和
  CORS；不要把 CORS 当成 CSRF 防护的替代品。

## 6. RBAC 权限管理

### 6.1 数据模型

复用项目现有 RBAC 表。常见关系如下：

``` text
用户 sys_user
  └── 用户角色关系 sys_user_role
        └── 角色 sys_role
              └── 角色权限关系 sys_role_permission
                    └── 权限 sys_permission
```

如果项目尚未建立 RBAC 模型，最小模型通常包括：

- 用户表。
- 角色表。
- 权限表。
- 用户角色关联表。
- 角色权限关联表。

具体字段、软删除、租户字段、审计字段及唯一索引应遵循项目现有数据库规范，不要在未检查项目的情况下另行定义一套冲突模型。

### 6.2 权限标识

使用稳定、可读的权限编码，例如：

- `system:user:list`
- `system:user:create`
- `system:user:update`
- `system:user:delete`
- `system:role:assign`

权限编码是后端鉴权的依据。菜单和按钮权限可以复用权限体系，但前端隐藏菜单或按钮不代表后端已完成权限控制。

### 6.3 方法级权限

在业务接口上使用 `@PreAuthorize`：

``` java
@PreAuthorize("hasAuthority('system:user:delete')")
@DeleteMapping("/{id}")
public ApiResponse<Void> delete(@PathVariable Long id) {
    userService.delete(id);
    return ApiResponse.success();
}
```

上面的 `ApiResponse` 仅为示例类型。实施时必须复用项目现有的统一响应类。

注意：

- `hasAuthority("system:user:delete")` 匹配完整权限标识。
- `hasRole("ADMIN")` 默认会匹配 `ROLE_ADMIN`，不要混淆角色和权限编码。
- 关键业务操作必须由后端进行鉴权。
- 如果权限被修改，需要明确权限何时生效。基础实现可以在每次 Token
  认证时重新加载用户及权限；确认性能需要后再设计缓存和失效机制。

## 7. API 设计

建议提供以下最小接口，具体 URL 应适配现有项目的 API 规范。

方法 路径 说明 认证
  -------- ------------------------- -------------------------- ------
`POST`   `/api/auth/login`         用户名密码登录 否
`POST`   `/api/auth/logout`        撤销当前 Token 是
`GET`    `/api/auth/me`            获取当前用户基本信息 是
`GET`    `/api/auth/permissions`   获取当前用户权限标识集合 是

登录响应至少包含 Token 和必要的用户信息。Token
类型、过期秒数、用户信息和权限字段的命名应遵循项目现有 API 规范。

未认证和权限不足必须使用统一响应格式，并通过 HTTP 状态码区分：

- `401 Unauthorized`：未登录、Token 无效、过期或已撤销。
- `403 Forbidden`：已认证，但没有访问资源所需的权限。

不要把所有异常都返回 HTTP
200，也不要把业务错误、认证错误和权限错误混为一类。

## 8. 浏览器、App 和小程序适配

后端使用统一的 Bearer Token 认证机制，各客户端根据自身安全能力保存凭证：

- **浏览器：** 优先评估安全 Cookie 或仅存于内存中的访问
  Token。避免将长期有效的凭证放在 `localStorage`；如果使用
  Cookie，必须正确处理 CSRF。
- **Android / iOS App：** 使用 `Authorization: Bearer`
  请求头；尽可能使用操作系统提供的安全存储能力。
- **小程序：** 使用 `Authorization: Bearer`
  请求头；使用平台允许的本地存储能力，并考虑设备丢失和凭证泄露风险。

后端不应仅凭客户端自报的 `clientType`
获得更高权限。客户端类型字段可以用于日志或后续策略，但不是可信的身份凭证。

第一阶段不实现按设备、客户端类型限制登录数量，也不将客户端类型与 Token
认证流程强耦合。

## 9. Redis 与安全要求

- Token 对应的 Redis Key 必须设置 TTL。
- 原始 Token 不得写入应用日志、异常日志或审计日志。
- 登录接口应考虑限流和暴力破解防护；若项目已有统一限流组件，应复用。
- 对用户禁用、删除或密码变更后的会话处理，应定义清晰策略。至少保证被禁用用户不能继续通过有效
  Token 访问受保护接口；可以在认证时检查账号状态，必要时撤销其 Token。
- Redis 故障时不能降级为"只要 Token
  格式正确就放行"。认证状态无法确认时，应按安全失败原则处理。
- 生产环境 Redis
  应配置访问控制、网络隔离和传输安全；不要暴露到不可信网络。
- 不要将密码、密码哈希或完整认证凭证放在 `LoginUser` 中。
- 确保用户权限来源于可信服务端数据，而不是请求参数或客户端提交内容。

## 10. 测试验收标准

AI Agent
实现后，至少应完成以下测试。优先使用项目现有测试框架和测试基建。

### 10.1 登录与 Token

- 正确的用户名和密码可以登录。
- 密码错误、用户不存在或账号不可用时，登录失败且不会签发 Token。
- 登录成功返回的 Token 是随机、不透明的凭证。
- Token 在 Redis 中存在有效记录和 TTL。
- 未携带 Token 访问受保护 API，返回 401。
- 携带无效、过期或已撤销 Token 访问受保护 API，返回 401。
- 有效 Token 可以访问需要登录但不要求额外业务权限的 API。
- 登出后，同一 Token 的后续请求返回 401。

### 10.2 权限控制

- 具有指定权限的用户可以访问对应 API。
- 缺少指定权限的已认证用户访问该 API 时返回 403。
- 未认证用户访问该 API 时返回 401，而不是 403。
- 前端隐藏按钮不能绕过后端的 `@PreAuthorize` 校验。
- 用户角色或权限发生变更后，行为符合项目明确的权限生效策略。

### 10.3 异常和安全

- 401 与 403 使用项目统一响应格式。
- 登录、Token 和密码不出现在日志中。
- Redis 不可用时不会绕过认证。
- 公开接口列表明确且范围最小。
- CSRF 配置与实际凭证传递方式相匹配。

## 13. 最终验收定义

本任务完成的标准是：

1. 项目可以正常编译并启动。
2. 用户可以使用用户名和密码登录并获取随机 Token。
3. 受保护 API 能够验证 Token，并正确识别当前用户。
4. 登出后 Token 对后续请求失效。
5. RBAC 权限可以通过 `@PreAuthorize` 生效。
6. 未认证和无权限请求分别返回正确的 401 / 403。
7. Redis 故障或 Token 无效时不会绕过认证。
8. 实现遵循现有项目结构，没有为尚未实现的多端策略引入无用抽象。
9. 关键功能有自动化测试，实施结果有清晰说明。
