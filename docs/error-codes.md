# 项目错误码使用说明

本项目使用 HTTP 状态和业务错误码共同表达失败原因。JSON 响应保持 `code/message/data` 三个字段；成功码为字符串 `"0"`，失败时
`data` 为 `null`。

```json
{
  "code": "COMMON_1010",
  "message": "所选部门存在用户关联，请解除后再试",
  "data": null
}
```

上述普通业务异常返回 HTTP 400。接口文档和客户端应通过 `code` 判断具体业务原因，`message`
用于展示，允许根据场景补充公开的字段提示。文件下载成功时仍返回文件内容。

## HTTP 状态

仅使用以下 7 种状态，由异常类型和处理场景决定，不登记业务错误码与 HTTP 状态的映射。

| HTTP 状态 | 处理场景                                                |
|---------|-----------------------------------------------------|
| 200     | 请求成功                                                |
| 400     | 普通 `BusinessException`、参数校验、请求格式、方法或媒体类型错误、上传超限、限流  |
| 401     | `AuthenticationException`、JWT 异常、未登录或会话失效           |
| 403     | `AccessDeniedException`、`DisabledException`、安全链权限拒绝 |
| 404     | 路由或资源不存在的框架错误                                       |
| 409     | `DuplicateKeyException` 等明确的数据重复                    |
| 500     | 未处理的系统异常、认证依赖故障、其他数据库完整性异常、接口返回值校验失败                |

同一业务错误码不会自动决定 HTTP 状态；普通 `BusinessException` 一律返回
400，即使错误码描述资源不存在或数据冲突。方法不支持、文件超限、限流等原因仍由响应中的业务错误码区分。

## 后端开发

1. 优先复用通用错误码；仅有独立处理需求时，在所属模块的 `error/XxxErrorCode` 枚举中新增错误码和默认消息，实现公共
   `ErrorCode` 接口。
2. 无需登记 HTTP 映射。`ErrorCodeRegistryTest` 检查所有枚举的错误码格式、唯一性和消息完整性。
3. 使用 `throw new BusinessException(CommonErrorCode.DATA_IN_USE, "所选部门存在用户关联，请解除后再试")`
   抛出业务异常。可通过第二个字符串参数补充公开消息，或传入原始异常作为 cause，使用默认提示并保留日志原因。
4. 不将 SQL、第三方服务异常原文或密钥放进公开消息。未知异常返回 `SYS_1001`，服务端保留完整日志。
5. 新增错误码后同步更新本表和相关接口说明。已发布的错误码保持语义稳定，不复用作其他错误。

通用抽象和认证码位于 `admin-common`；MVC 和 Security 适配位于 `admin-framework`；业务码由各业务模块维护。业务错误码接口不依赖
Spring Web。

`ApiResult` 仅封装传入的业务错误码、消息和数据，不进行 HTTP 状态码转换。HTTP 状态由异常处理器和安全处理器直接设置。

旧 `BadRequestException` 构造方法保留，兜底码为 `COMMON_1005`。显式状态仅保留 400、401、403、404、409、500；其余 4xx 归入
400，其余状态归入 500。新增业务应使用明确的错误码。

业务中的实体不存在、数据已存在统一使用 `BusinessException` 携带错误码和公开消息，无需单独定义异常类。以下两种业务校验均返回
HTTP 400，分别通过 `COMMON_1002`、`COMMON_1003` 区分原因：

```java
throw new BusinessException(CommonErrorCode.RESOURCE_NOT_FOUND, "用户不存在");
throw new

BusinessException(CommonErrorCode.DATA_ALREADY_EXISTS, "用户名已存在");
```

MVC 参数校验、JSON 格式、参数类型、请求方法、媒体类型、文件大小、数据库唯一键冲突均由统一异常处理器处理。数据库并发唯一键冲突和业务重复预检查均使用
`COMMON_1003`，通过消息说明具体字段。容器 `/error` 由 Spring Boot 默认错误控制器处理，不保证返回 `code/message/data` 结构。

全局处理器按业务、认证、权限、校验、请求格式、上传超限、数据重复、框架请求异常和系统兜底分类。认证服务内部异常和非重复的数据完整性异常按系统故障处理；只有明确的凭据错误返回
`AUTH_1001`。参数校验返回公开约束提示，接口返回值校验失败返回通用系统消息并记录异常。

## 认证和前端

- 未提供凭证、Token 无效、JWT 过期或 Redis 会话已失效统一返回 `AUTH_1005`。验证码错误和过期统一返回 `AUTH_1007`。
- 项目生成的 Token 不设置 JWT 到期时间，日常有效期由 Redis 会话维护。主动退出、被踢下线和自然过期统一视为会话失效。
- 登录用户不存在和密码错误统一返回 `AUTH_1001`，不通过错误码区分这两种原因。
- Token 失效不会阻止访问登录和验证码等公开接口。认证依赖服务故障返回 `SYS_1001`，不会被误判为登录失效。
- `request.js` 在 Promise 拒绝时提供 `error.code`、`error.businessCode`、`error.message`、`error.httpStatus`，原始响应仍可从
  `error.response` 读取。
- 仅登录失效相关码触发重新认证；登录凭据错误展示消息。兼容旧 HTTP 401 响应。
- `PERMISSION_1001` 可跳转权限提示页；数据范围、角色级别等业务拒绝停留在当前页面并显示具体提示。
- 上传工具和 Blob 下载失败共用错误解析，解析完成后拒绝 Promise。网络断开或超时也会返回可展示提示。
